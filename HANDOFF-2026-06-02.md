# Handoff — 2026-06-02 (4.4.166)

Picked up out-of-context (wrong chat) but the entry-killer fix is done, committed, and released. Cameras + alarm still need a real port. Details below so you can continue.

## What broke
HA core on the prod host is now on **python3.14** with the **rewritten built-in Tuya integration** (uses `tuya_device_handlers` lib + new description-based entity base classes). The fork (4.4.165) targets the old API. After "old xtend" was removed + HA/Tuya upgraded, several things broke. Logs: `~/Downloads/home-assistant_2026-06-02T10-58-44.653Z.log`.

Three distinct failures seen:
1. **Entry-killer (fixed): `KeyError: 'min'`**
   `sensor.py:2067 async_add_generic_entities` → `sensor.py:140 xt_get_default_definition` → upstream `tuya_device_handlers/type_information.py:157` does `int(parsed["min"])` unconditionally. An integer DP (a valve `countdown`/`delay_task`) has type_data with no `min` → KeyError. Uncaught, it propagated through `process_post_setup_callback` → `on_loading_finalized` → `async_setup_entry`, **failing the whole account entry** → every device dropped, automations disabled (`Unknown device '4698c61f...'`).
2. **Cameras (still broken): `TypeError: TuyaCameraEntity.__init__() missing 1 required positional argument: 'description'`**
   `camera.py:184` calls `super(XTEntity, self).__init__(device, device_manager, definition=definition)`. New upstream `TuyaCameraEntity` wants a `description` (a `TuyaCameraEntityDescription`), not a `definition` (`TuyaCameraDefinition`) — different objects in the rewritten model. Already isolated (4.4.163) so it only drops cameras, not the entry.
3. **Alarm panels (still broken): `TypeError: 'AlarmControlPanelEntityDescription' object is not iterable`**
   `alarm_control_panel` platform iterates a descriptor that is now a single object, not a tuple. Also the `Merging of descriptors failed, non-matching include/exclude tuple VS dict` warnings are the same descriptor-shape change.
4. **Duplicate unique IDs** (numbers/calendar) — fork re-registers entities the rewritten built-in Tuya already owns (`tuya.<id>countdown already exists` etc.). Cosmetic-ish but noisy; revisit during the port.

## What I changed (shipped as 4.4.166)
Commit `6ea016c8`, tag `v4.4.166`, GitHub release on `fork` (raukaute/xtend_tuya).

Only fix: guard `xt_get_default_definition` in `sensor.py` so an incomplete DP can't fail the whole entry — same isolation pattern as the 4.4.163 camera fix.

```python
# custom_components/xtend_tuya/sensor.py  ~line 140
try:
    return get_default_definition(
        device=device, dpcode=dpcode, wrapper_class=description.wrapper_class
    )
except (KeyError, TypeError, ValueError) as err:
    LOGGER.warning(
        "Skipping generic sensor for device=%s dpcode=%s — incomplete DP definition (%s)",
        getattr(device, "id", "?"), dpcode, err,
    )
    return None
```
`if definition := ...` at the call site already treats `None` as "skip this DP", so the loop continues and the entry finishes. The malformed valve DP loses its auto-generated generic sensor (cosmetic). `manifest.json` bumped 4.4.165 → 4.4.166. `python -m py_compile` clean.
